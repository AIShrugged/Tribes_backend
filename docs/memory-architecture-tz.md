# ТЗ: Архитектура памяти для Tribes Bot

**Версия:** 1.0  
**Дата:** 2026-04-21  
**Статус:** Draft  
**Автор:** CTO (Paperclip Agent)

---

## 1. Обзор

Этот документ описывает техническое задание (ТЗ) на реализацию механизма «памяти» для Tribes Bot — AI-ассистента, интегрированного в Telegram и управляющего задачами через API Tribes. Основная цель: бот должен помнить контекст взаимодействий с пользователем, чтобы давать релевантные ответы, делать персональные рекомендации и автоматизировать повторяющиеся сценарии.

**Ключевой принцип:** архитектура памяти определяется юзкейсами, а не наоборот. В этом документе сначала описаны конкретные сценарии, а затем — требования к системе.

---

## 2. Глоссарий

| Термин | Описание |
|---|---|
| **Память (Memory)** | Сохранённый контекст взаимодействия пользователя с ботом, используемый в последующих сессиях |
| **Сессия (Session)** | Одна непрерывная последовательность сообщений между пользователем и ботом |
| **Юзкейс (Use Case)** | Конкретный сценарий использования памяти, описанный с точки зрения пользователя |
| **Вектор (Embedding)** | Числовое представление текста для семантического поиска |
| **Контекстное окно** | Ограниченный объём информации, передаваемый в LLM за один запрос |
| **Племя (Tribe)** | Команда/группа в платформе Tribes |

## 3. Юзкейсы

### UC-1: Диалог с ботом о приоритетах задач

**Сценарий:**  
Пользователь несколько раз обсуждал с ботом свои рабочие приоритеты. Например: «Я сейчас фокусируюсь на релизе v2.0 и не хочу брать другие задачи до 25 апреля». Через 2 дня пользователь пишет: «Что мне сделать сегодня?» — бот должен вспомнить контекст и не предлагать задачи вне текущего фокуса.

**Триггер:**  
- Пользователь явно говорит боту о приоритетах, дедлайнах, фокусе  
- Пользователь просит сформировать план на день/неделю  

**Что нужно помнить:**  
- Текущий фокус/спринт пользователя  
- Временные ограничения («до 25 апреля»)  
- Задачи, от которых пользователь сознательно отказался  

**Формат хранения:**  
```json
{
  "type": "user_focus",
  "user_id": 123,
  "focus": "Релиз v2.0",
  "valid_until": "2026-04-25",
  "excluded_task_types": ["support", "ad-hoc"],
  "created_at": "2026-04-21T10:00:00Z"
}
```

**Тест:**  
1. Пользователь: «Я фокусируюсь на релизе v2.0 до 25 апреля»  
2. (2 дня спустя) Пользователь: «Что делать сегодня?»  
3. Ожидаемый ответ: бот предлагает только задачи, связанные с v2.0, и добавляет: «Помню, что ты фокусируешься на релизе до 25 апреля»  
4. Негативный тест: бот НЕ должен предлагать support-задачи

### UC-2: Напоминания о встречах и событиях

**Сценарий:**  
Пользователь просит бота напомнить ему о встрече: «Напомни мне о стендапе завтра в 10:00». Бот должен сохранить напоминание и отправить уведомление в нужное время. При следующей сессии пользователь может спросить «Что у меня запланировано?» — бот должен показать все активные напоминания.

**Триггер:**  
- Явный запрос: «Напомни», «Напомни мне», «Remind me»  
- Создание события через команду `/remind`  
- Интеграция с календарём (будущая версия)  

**Что нужно помнить:**  
- Дата и время напоминания  
- Текст напоминания  
- Статус (активно / отправлено / отменено)  

**Формат хранения:**  
```json
{
  "type": "reminder",
  "user_id": 123,
  "text": "Стендап",
  "remind_at": "2026-04-22T10:00:00Z",
  "status": "pending",
  "created_at": "2026-04-21T15:00:00Z"
}
```

**Тест:**  
1. Пользователь: «Напомни мне о стендапе завтра в 10:00»  
2. Бот: «Окей, напомню тебе о стендапе 22 апреля в 10:00»  
3. В 09:55 22 апреля бот отправляет: «Через 5 минут стендап!»  
4. Пользователь: «Что у меня запланировано на завтра?» → бот перечисляет все напоминания

### UC-3: Персональные предпочтения и стиль работы

**Сценарий:**  
Пользователь в первые дни работы с ботом указал свои предпочтения: «Я работаю с 9 до 18, не беспокой меня по выходным» и «Предпочитаю получать задачи списком, а не текстом». Бот должен учитывать эти настройки при каждом взаимодействии — форматировать ответы правильно и не слать уведомления вне рабочего времени.

**Триггер:**  
- Пользователь явно сообщает предпочтение  
- Пользователь корректирует формат ответа бота («Нет, покажи это как список»)  
- Первичная настройка через `/settings`  

**Что нужно помнить:**  
- Рабочее время  
- Формат ответов (список / текст / таблица)  
- Язык общения (ru/en)  
- Часовой пояс  

**Формат хранения:**  
```json
{
  "type": "user_preferences",
  "user_id": 123,
  "work_hours": {"start": "09:00", "end": "18:00", "timezone": "Europe/Moscow"},
  "work_days": ["Mon", "Tue", "Wed", "Thu", "Fri"],
  "response_format": "list",
  "language": "ru",
  "updated_at": "2026-04-21T10:00:00Z"
}
```

**Тест:**  
1. Пользователь: «Я работаю с 9 до 18 по московскому времени»  
2. Бот сохраняет и подтверждает  
3. Пользователь создаёт задачу в субботу в 20:00 → бот сохраняет, но НЕ отправляет уведомления  
4. В понедельник в 9:00 бот сообщает о задачах, накопленных за выходные

### UC-4: История обсуждений задач в команде

**Сценарий:**  
В чате племени обсуждалась задача TASK-42. Участники обменялись мнениями, приняли решение об архитектуре. Через неделю новый участник спрашивает бота: «Почему мы выбрали микросервисы для модуля уведомлений?» — бот должен найти соответствующее обсуждение и дать ответ со ссылкой на принятое решение.

**Триггер:**  
- Вопрос о причинах принятого решения  
- Запрос истории обсуждения конкретной задачи (`/history TASK-42`)  
- Новый участник присоединяется к племени  

**Что нужно помнить:**  
- Ключевые решения по задачам (Architecture Decision Records — ADR)  
- Кто участвовал в обсуждении  
- Дата принятия решения  
- Аргументы за/против  

**Формат хранения:**  
```json
{
  "type": "team_decision",
  "tribe_id": 456,
  "task_id": "TASK-42",
  "decision": "Выбраны микросервисы для модуля уведомлений",
  "rationale": "Нужна независимая масштабируемость, команда уже знает Docker",
  "participants": [123, 124, 125],
  "decided_at": "2026-04-14T14:00:00Z"
}
```

**Тест:**  
1. Команда обсуждает в чате: «Выберем микросервисы, потому что X, Y, Z» — бот распознаёт решение и сохраняет  
2. Новый участник: «Почему мы выбрали микросервисы?»  
3. Бот отвечает: «14 апреля команда решила использовать микросервисы для модуля уведомлений: [X, Y, Z]. Участвовали: @alice, @bob, @carol»

### UC-5: Отслеживание прогресса и достижений пользователя

**Сценарий:**  
Бот накапливает статистику: сколько задач пользователь закрыл, какова его скорость, насколько он укладывается в дедлайны. Раз в неделю бот отправляет персональный отчёт: «На этой неделе ты закрыл 12 задач, это на 20% больше, чем на прошлой». При постановке нового дедлайна бот предупреждает: «Обычно задачи такого типа занимают у тебя 3 дня».

**Триггер:**  
- Закрытие задачи пользователем  
- Истечение дедлайна  
- Запрос `/stats` или еженедельное расписание  

**Что нужно помнить:**  
- Количество закрытых задач по неделям  
- Среднее время выполнения по типам задач  
- Процент задач, выполненных в срок  
- Стрики (серии успешных недель)  

**Формат хранения:**  
```json
{
  "type": "user_stats",
  "user_id": 123,
  "week": "2026-W16",
  "tasks_completed": 12,
  "tasks_on_time": 10,
  "avg_completion_time_by_type": {
    "bug": 1.5,
    "feature": 4.2,
    "review": 0.5
  },
  "streak_weeks": 3
}
```

**Тест:**  
1. Пользователь закрывает 12 задач за неделю — система фиксирует  
2. В понедельник бот автоматически отправляет еженедельный отчёт  
3. При создании новой задачи типа «feature» бот добавляет: «Обычно у тебя уходит ~4 дня на такие задачи»

### UC-6: Контекст незавершённых диалогов

**Сценарий:**  
Пользователь начал с ботом планирование спринта, заполнил часть, но прервался. Через час возвращается и пишет «продолжим». Бот должен восстановить контекст и продолжить с того места, где остановились, не заставляя пользователя повторять всё заново.

**Триггер:**  
- Пользователь пишет «продолжим», «давай продолжим», «continue»  
- Пользователь возвращается в тот же чат после паузы более 10 минут  

**Что нужно помнить:**  
- Незавершённый workflow (шаг, на котором остановился)  
- Уже заполненные данные  
- Тип задачи (планирование спринта, создание задачи, и т.д.)  

**Формат хранения:**  
```json
{
  "type": "pending_workflow",
  "user_id": 123,
  "workflow": "sprint_planning",
  "current_step": 3,
  "collected_data": {
    "sprint_name": "Sprint 14",
    "goal": "Запустить onboarding v2",
    "team_members": [123, 124]
  },
  "expires_at": "2026-04-22T10:00:00Z"
}
```

**Тест:**  
1. Пользователь начинает `/plan_sprint`, заполняет название и цель, уходит  
2. Через 30 минут пишет «продолжим»  
3. Бот: «Продолжаем планирование Sprint 14. На каком шаге были: выбор команды. Кто в команде?»  
4. Негативный тест: незавершённый workflow автоматически отмечается как устаревший через 24 часа

## 4. Требования к системе памяти

На основе юзкейсов выделяем следующие требования:

### 4.1 Типы памяти

| Тип | Юзкейс | TTL | Объём |
|---|---|---|---|
| **Short-term** (сессионная) | UC-6 | 24 часа | Маленький (текущий диалог) |
| **Medium-term** (пользовательская) | UC-1, UC-3, UC-5 | 30–90 дней | Средний (профиль + статистика) |
| **Long-term** (командная) | UC-2, UC-4 | Постоянно | Большой (решения, история) |

### 4.2 Структура хранилища

```
Memory Layer
├── Session Store (Redis)         # UC-6: незавершённые диалоги
│   └── TTL: 24 часа
├── User Profile Store (PostgreSQL) # UC-1, UC-3, UC-5: предпочтения, фокус, статистика
│   └── Indexed by user_id
├── Reminder Store (PostgreSQL)   # UC-2: напоминания с планировщиком
│   └── Indexed by remind_at
└── Knowledge Base (PostgreSQL + pgvector) # UC-4: решения, история
    └── Vector embeddings для семантического поиска
```

### 4.3 Интерфейс доступа к памяти

Для LLM-агента реализовать инструменты (MCP-tools или внутренние):

```
memory_save(type, user_id/tribe_id, data)   → сохранить запись
memory_get(type, user_id/tribe_id)          → получить последние N записей
memory_search(query, scope)                 → семантический поиск
memory_delete(type, id)                     → удалить запись
```

### 4.4 Безопасность и приватность

- Память пользователя изолирована: агент tribe не может читать личную память другого пользователя  
- Командная память доступна только членам племени  
- Возможность удаления всей памяти по запросу (`/forget me`)  
- Логирование всех операций чтения/записи для аудита  

### 4.5 Ограничения контекстного окна

Механизм «компрессии» памяти: при наполнении контекстного окна система автоматически:
1. Выбирает наиболее релевантные воспоминания к текущему запросу (семантический поиск)  
2. Суммаризирует старые воспоминания, объединяя похожие  
3. Удаляет устаревшие (TTL истёк)

## 5. Предлагаемая реализация (фазы)

### Фаза 1 (MVP, 2 недели)

- UC-4: Векторный поиск по истории решений команды (pgvector)
